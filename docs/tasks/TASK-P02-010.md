## Watcher behaviour

`ops/rerun/run2-watcher.sh <first-run pid>`, started detached under `caffeinate -i -s`:

1. It checks that the pid is the first run's `capture.py live --out ~/gladiator-data/live-7d` process (abort 1). It then re-checks that identity every 60 s until the process exits, so a reused pid ends the wait instead of stalling it.
2. It requires a non-empty `~/gladiator-data/live-7d/live-summary.jsonl`. `cli.main` writes this file only after `cmd_live` returns, so a crash or kill leaves it missing (abort 2).
3. It refuses to start if `~/gladiator-capture-run2` or `~/gladiator-data/live-7d-run2` already exists (abort 3).
4. It fetches `origin/master`, up to 10 times 60 s apart (abort 4 if every attempt fails). It records the revision, and whether `c2b2aa8` (the head of #33) is an ancestor of it. That check assumes merge commits, which this repository uses; a squash merge would report "no".
5. It extracts that revision with `git archive` into `~/gladiator-capture-run2`, under `pipefail`, checks that `capture.py` exists there and writes `REVISION` (abort 5).
6. It runs the offline tests with `python3 -I -B -m unittest discover -s tests` (abort 6 if any fail).
7. It then `exec`s `caffeinate -i -s /usr/bin/python3 -I -B capture.py live --out ~/gladiator-data/live-7d-run2 --seconds 604800`, which has the same pairs, depth and duration as DEC-064. Stdout and stderr go to `run.log` in that directory. It aborts with 7 if it cannot create or enter the directories, and with 8 if the `exec` fails (`execfail` is set). macOS `caffeinate` runs the command in its own pid, so the rerun's Python keeps the watcher's pid.

Each abort is logged, and an aborted watcher never starts the rerun. The repository checkout is only fetched, so its working tree and branch stay as they are. `RUN_SECONDS` overrides the duration for dry runs only.
