## Objective and observable result

Today a book's validity exists only in the capture's operational `events.jsonl` and in analysis reports. Under DEC-075 it becomes a record that replay reads like any other event. The records are derived **from the raw frames alone**, which the raw store holds, so a replay never needs `events.jsonl`. Three kinds are derived:

1. **`VenueStatus`**: one record per `status` channel frame, with the fields of event contract §4.4: `system`, `api_version`, `connection_id`, `version`, and the received `upcoming_maintenance` list unchanged.
2. **Book-invalid `GapInterval`s**: one set per pair, `gap_class` `data_gap`, `availability_state` `SOURCE_UNAVAILABLE`. A book is invalid over:
   - (a) **start**: from the first frame of the run until that pair's first book snapshot (initial sync);
   - (b) **silence** (DEC-071): from the last frame on any channel to the next frame, when they are more than 15 s apart;
   - (c) **reconnect**: a `status` frame whose `connection_id` differs from the previous one marks a new connection. The book is invalid from the last frame before that status frame until the pair's first book snapshot after it;
   - (d) **resync within a connection**: a book snapshot for a pair with no new `connection_id` since the last one (the capture resubscribes after a checksum mismatch). The book is invalid from the pair's last book frame before it until the snapshot;
   - (e) **open end**: an interval still open at the run's last frame ends there, flagged `open_at_end`.

   Overlapping or adjacent intervals for a pair are merged. `evidence` names the rules that produced the interval. `available_at` is the receive time of the frame that ends it (a snapshot or the next frame), because the interval is known only then.
3. **`MaintenanceWindow`**: a new derived record type, for the R-4 exclusion (DEC-074). It is **not** book invalidity: data can flow normally during an announced window. It reuses `live_analysis.announced_maintenance`, so the rule is applied once, the same way as in the analysis. Each record carries `source` (`status` for a `maintenance` system state, `announced` for an announced `spot_ws` item), `event_id`, `title`, the announced and excluded times, `first_listed` and `unlisted_at`, and `withdrawn` (unlisted before its start, so nothing is excluded).

**Not changed:**
- Raw frames, the capture, and `normalize()`'s existing book and trade records.
- The running 30-day job and its code copy.

The derivation is a pure function over frames in receive order across all of a run's segments, so its output is deterministic.
